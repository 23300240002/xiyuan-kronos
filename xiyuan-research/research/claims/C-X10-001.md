## 1. 代码证据

1. `KronosLocal/deps/Kronos/model/kronos.py` 的 `Kronos.decode_s1` 在 Transformer 和 RMSNorm 后返回 `(s1_logits, x)`，其中 `x` 的形状是 `[B,T,d_model]`。这提供了一个可读取的低频 token-level context，但没有声明它是预测充分统计量。
2. 本地 tokenizer 配置为 `d_in=6`、`s1_bits=s2_bits=10`；Kronos-small 权重配置为 `d_model=512`、`n_layers=8`。因此当前小模型的低频 context 维度是 512，不能直接套用模型 D 的一维 $Z_L$ 记号。
3. `KronosPredictor.predict/predict_batch` 先对每个历史窗口独立计算均值和标准差，再调用自回归预测；公共返回值是未来 OHLCVA 路径。`common/service.py` 的 `/predict_batch` 也只返回预测路径和耗时，没有 context、配对键或对齐损失。
4. `KronosEnhanced` 是另一套简化 Transformer 架构，代码明确写着真实实现应加载预训练权重；不能把它的 fusion 输出当成 KronosLocal 的原始 hidden。

## 3. 对 X-10 的严格判定

- **已回答的部分：** 真实 Kronos 有可取出的低频内部状态；可以构造 `Z_L` 的工程候选。
- **仍未回答的部分：** 该 context 是否与高频编码器输出按同一预测时点配对；两路是否在同一尺度；预测头是否实际同时使用两路；部署时两路是否都可得；项目的 `L_align` 究竟是完整 context 距离、共享投影距离还是别的目标。
- **因此当前状态：** `FORMALIZED`（接口对象已定位）+ `BLOCKED`（项目对齐定义尚未确定）。不能据此启用 `delta>0`，也不能把模型 D 的 $R_H,R,\Delta I$ 写成项目保证。

## 4. 最小实现路线

1. 写一个只负责 `KronosLocal -> context` 的 adapter，输入必须是预测时点以前的 OHLCVA 和时间戳，输出最后一个可用 token 的 `[B,512]` 向量及 `(asset, cutoff_time)` 元数据。
2. 对高频数据只做同一 cutoff 的聚合和编码；禁止使用 cutoff 之后到标签结束之间的统计量。
3. 先记录 `delta=0` 基线和不对齐的双路预测头；只有项目确认共享子空间后，才加入一个有明确投影和尺度锚点的候选 `L_align`。
4. 保留高频私有残差给预测头；“全量 context 平方距离”只能作为消融，不可默认是正确目标。
5. 用同一时间切分和冻结评估集比较低频、双路无对齐、双路共享投影对齐三组；报告风险差、置信区间、缺失高频时的回退行为和部署延迟。

## 5. 失效边界与不能声称的内容

- `context` 是模型内部 token 表征，不等于条件期望，也不自动满足模型 D 的线性高斯假设。
- 形状检查通过不代表表征有预测增量信息。
- 现有代码没有证明时间戳、标签窗口或高频数据已经正确配对；这仍需数据字典和实际样本审计。
- `KronosEnhanced` 的随机/简化 backbone 不能作为真实 Kronos 的接口证据。

## 6. 已实现的最小 adapter

`scripts/kronos_context_adapter.py` 已实现只读 adapter：对每个窗口检查严格递增时间戳、最后观测时间等于 `cutoff_time`、OHLCVA 有限；按 KronosPredictor 的窗口统计量归一化；调用真实 `tokenizer.encode(..., half=True)` 与 `model.decode_s1(...)`；只返回最后一个 observed token 的 context 和配对元数据。它不调用自回归生成，也不加入 `L_align`。

实际运行命令：

```text
python        # conda env: kronos \
  research/scripts/kronos_context_adapter.py
```

输出：`context_last=(1,512)`，`pair_key=('demo','2026-01-01T09:37:00')`，`KRONOS_CONTEXT_ADAPTER_SMOKE: PASS`。
