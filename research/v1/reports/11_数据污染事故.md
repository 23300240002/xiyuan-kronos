# 11 · 30 天 L2 解析数据污染事故（P0）

> 发现：2026-10-26 · 发现者：接手 Agent（核对 parse30c 日志与产物时）
> 状态：**已定位根因、已停止污染进程、修复与重跑进行中**
> 影响面：**仅 `l2/parsed_30d`**。未污染任何已发表结论，也未产出任何下游张量。

---

## 一、一句话结论

**`l2/parsed_30d` 里绝大部分 parquet 的文件名日期是假的。**

同一只票在不同日期 tag 下的文件，内容**互相重复**：11 个已完成日期里只有 **6 组不同签名**，
即约 **45% 的"日数据"是别的日期的副本**。按此数据建张量，L2 截面实验会得到
"看起来正常但完全错误"的结果——和历史上 `test_eval` 选错权重是同一类事故。

## 二、铁证

### 证据 1：日志自相矛盾（最快的一眼识别）

```
[l2] 目录模式：20 个归档
[l2] (1/20) 20241022.7z
[l2] 票池过滤：7,240 → 500 个行情表     ← 过滤是对的

```

## 三、根因

`$W/code/v1/xy/data/l2.py` 的 `run()`：

```python
# 第 189 行：在【整个输出根目录】上递归找行情.csv
stocks = sorted([p.parent for p in out.rglob("行情.csv")])
...
# 第 201 行：用【当前归档的日期】给它们命名写出
feat.to_parquet(out / f"{date_tag}_{name}.parquet", index=False)
```

其中 `out` 是输出根 `l2/parsed_30d`，而 `z.extract()` 把当天 500 只票解压到
`out/<YYYYMMDD>/<code>/`，**解压后从不清理**。

于是第 N 个归档运行时，`rglob` 扫到的是**前 N-1 天残留的解压目录 + 当天新解压的**，
再统统按第 N 天的 `date_tag` 重写一遍 → 文件名是第 N 天，内容是历史某天的。

**为什么塌缩成 6 组而非全部相同**：写出时是"后写覆盖先写"，
而 `imap_unordered` 的完成顺序不确定 → 每个 `(tag, stock)` 最终保存的是
**任意某一天的副本**。这也解释了为什么分布不是均匀的。

根因属于 `reports/08` 已记录的「解析残留未清理」类问题，
但当时只考虑了磁盘，没考虑到它会**反向污染读取范围**。

## 四、为什么之前没被发现

1. **日志有两个数字，但没人对账**：`票池过滤 500` 和 `待处理 59852`
   相隔 4 行、由不同代码路径打印，看起来都"正常"。
2. **`path_date` 列误导**：它按 date_tag 写入，永远是"对"的，
   任何基于该列的校验都通过。
3. **只有"看起来跑完了"的外观**：进程正常退出、日志正常 `ok=NNNNN`、文件数只多不少。
   这与 `HANDOFF §9 纪律` 里 `test_eval` 选错权重是**同一种失败模式**：
   *不会报错，只会静默给错答案*。
4. 解析还没跑完就没人去建张量，所以**下游尚未被污染**——这是本次不幸中的万幸。

## 六、修复方案

`run()` 中把 rglob 范围从"整个 out"收到"本次解压的子树"：

1. 从 `z.getnames()` 的命中项直接推出本次的 500 个目录，逐个处理，**不做目录扫描**；
2. 解压与处理都在**临时目录**内完成，处理完 `rmtree`，保证不残留；
3. 主循环再加一道**幂等校验**：若同一 `(tag, code)` 被处理超过一次则报错退出。

第 3 点是关键——**让这类 bug 从"静默"变成"崩溃"**，符合 `HANDOFF §9` 的纪律要求。

## 七、验收标准（不满足不算修好）

- [ ] 每个日期的 parquet 数 == **500**
- [ ] parquet 总数 == 日期数 × 500
- [ ] **相邻日期同名票内容不同**（抽 000001.SZ / 000002.SZ 实测 `allclose=False`）
- [ ] 同一票在 30 个日期上的签名**两两不等**（即 30 组不同签名，不再是 6 组）
- [ ] 日志每段显示"待处理 500"，不再出现 59852
- [ ] 处理完 `parsed_30d` 下**不残留** `<YYYYMMDD>/<code>/` 解压目录
- [ ] 与 5min K 线的日期、票池完全对齐

**签名去重校验是本次新增的强制项**（上面第 4 条）：这是唯一能抓住"文件名对、内容错"的检查。

---

## 八、教训（写进 checklist）

1. **"数量对不上"是最便宜的自检**。过滤后 500 却处理 59852，这一条就能在 10 秒内发现问题。
   → 任何批量任务，日志里**打印"预期数 vs 实际数"并在不等时直接抛错**。
2. **不要用数据自带的元数据列校验数据**（`path_date` 因为随写入而正确）。
   校验必须用**跨记录的内容签名**（行数/首值/末值/校验和）。
3. **中间产物目录不能同时当解压暂存区**。输入暂存与输出目录必须分离。
4. **解压残留必须清理**，否则既吃磁盘（120G）又污染后续读取范围。
5. 本次与 `test_eval --match`（D1）、`best_val_ic=max`（纪律 0）同属一类：
   **静默错误 > 显式崩溃**。工程上要主动把静默错误转成崩溃。

## 九、本轮追加发现（同一次接手，三个新 bug）

在写交接文档时又核实出三个问题，都已实测确认。

### Bug A · `--loss mix` 的 MSE 项被 rank 项淹没（量纲差 ~450 倍）

| 配置 | ep00 train_loss |
|---|---|
| `--loss mse`（moe2-M1 s0） | **0.0015418** |
| `--loss rank`（arm1 rank s0） | **0.6921628** |
| `--loss mix`（arm1 mix s0，实测） | **0.69418** |

`loss = F.mse_loss(pl, yb) + lam * rank_loss(pl, yb)`，λ=1 默认。
0.69418 − 0.69216 ≈ 0.0020 ≈ mse 项，**占总 loss 的 0.29%**。

**结论：`--loss mix` 实际上就是 `--loss rank`。** 此前"mse+rank 混合"的实验
（若有）不能当作混合损失看待。修法：两项做尺度归一后再加权，
并验证两项梯度都非零，而不是只看总 loss。

### Bug B · 队列幂等检查路径与实际输出路径不一致

`gpu_master2.sh:15` 判重用的路径：
```
runs/arm/arm{arm}_{fq}_s{s}_h64_d0.3_w0.1_{loss}_{micro}_{size}_{fus}/result.json
```
但 `run_arm.py:446` 实际写到：
```
runs/arm/arm{arm}_{freq}_s{seed}_h{head_hidden}_d{dropout}_w{wd}_{loss}_{micro}_{size}_{fusion}_{label}
```

差一个 `_raw` 后缀（`label` 默认 `raw`）。**后果：队列永远认为"没跑过"，
会重复跑已经完成的实验**——这与历史上"3 个重复队列"的事故是同一类浪费。

修法：两处统一；更稳的做法是队列直接从 `run_arm` 导入路径构造函数，杜绝再次漂移。

### Bug C · 旧的 mse 基线目录没有 `_raw` 后缀

`runs/arm/arm?_5min_s?_h64_d0.3_w0.1/`（无后缀）是**加 `label` 之前**跑的，
仍是最常引用的 5min 基线。现在按 `*_mse_m1_small_xattn_raw` 去 glob 会**全部落空**
（实测 `arm1 s0/s1/s2 MISSING`）。引用基线数字时注意用无后缀的旧路径。
